\section{Test}

La parte di testing può solo confermare la presenza di difetti, bug, ma non la loro assenza.

Perché testare allora?
\begin{itemize}
  \item Un test verifica automaticamente il comportamento del codice
  \item Non dimostra l'assenza di errori
  \item Aumenta la confidenza nel sistema
  \item Previene regressioni nel tempo
\end{itemize}

I test sono fondamentali per mantenere codice di qualità.

\paragraph{Esempio: problema reale - divisione per zero}

\begin{minted}[breaklines]{rust}
fn divide(a: i32, b: i32) -> i32 {
  a / b
}
\end{minted}

Funziona fino a che $b\,\neq 0$. Questo caso limite, a run-time, farà andare in panic il programma.
Per accorgercene automaticamente dobbiamo introdurre il concetto di \textit{unit test}, test di unità.

Ci sono molte tipologie di test. La più semplice, fornita direttamente dall'IDE di sviluppo,
è l'analisi statica del programma, che ci avverte in caso di variabili non usate, errori di sintassi, etc.

\section{Test di unità}

Un test di unità, o \textbf{unit test}, valuta, in maniera isolata, il comportamento di un singolo
componente software, funzione, struttura dati, etc, indipendentemente dal resto
del sistema. Ne sollecita il comportamento tipico, ovvero confrome all'uso per
cui è stato progettato, sia quello agli estremi o oltre il suo previsto capo di
utilizzo.

Tale sollecitazione viene esercitata tramite frammenti di codice che invocano il
componente e verificano che esso risponda in modo atteso, confrontando i
valori ritornati dalla funzione/contenuti nella struttura dati dopo la sollecitazione
con valori/ccondizioni di essere attesi sulla base delle specifiche.


% Il test di unità è una funzione che mira ad usare in maniera isolata e atomica
% un componente software, predicendone il risultato.

Nel caso di Rust, troviamo la macro \mintinline{rust}|assert| e \mintinline{rust}|assert_eq|,
che verificano che l'aspettativa sia soddisfatta o meno.
% Nel caso di Rust trovmiao la macro assert o notAssert che verifica che l'easpettativa sia
% soddisfatta o meno.

Nell'ambiente Cargo, i test vengono eseguiti con il comando \verb|cargo test|.

% Con cargo test vengono esesguite le funzioni di test per verificare se il codice
% è sano o meno, anche aggiungendo codice.


% I test sollevano un comportamento

\begin{minted}[breaklines]{rust}
#[test]
fn test_divide() {
  assert_eq!(divide(6,3), 2);
}
\end{minted}

\begin{tcolorbox}
  \textbf{Nota:} Verifica un caso tipico ma non copre errori, un test singolo non
  basta!
\end{tcolorbox}

Proprio per questo motivo dobbiamo andare a testare i casi limite.

Gli unit test sono considerati test with box, ovvero test che si basano sulla conoscenza del codice sorgente, e
normalmente sono scritti ed eseguiti direttamente dal programmatore.
In questo caso siamo in grado di predire che determianti parateri in ingresso portano a un certo risultato in uscita.

% Gli unit test sono dei with box text scritti direttamente dal programmatore. Siamo
% in grado di predire che determianti parateri in ingresso portano a un certo risultato in uscita.

% Eg granello di sabbia in un orologio meccanico vs goccia d'acqua in un orologio al quarzo.

\begin{itemize}
  \item Presuppongono la conoscenza dei  meccanismi interni al componente, allo scopo di verificare come
        questi reagiscono in presenza di casi limite
  \item Il loro numero dipende dalla complessità ciclomatica del modulo testato
  \item La loro qualità è alla base del processo di refactoring cui un artefatto software tipicamente è soggetto
        nel corso del suo naturale ciclo di vita
\end{itemize}

Il costo delle modifiche che vengono evidenziate da questo tipo di test è
normalmente basso. Tuttavia i benefici che la scrittura di test ben fatti portano alla
qualità del codice sono alti e compensano abbondantemente nel medio termine i
maggiori costi dovuti alla scrittura dei test.

\section{Test dei casi limite}

È fondamentale testare i casi limite. Per questo Rust offre la possibilità
di scrivere \mintinline{rust}|#[should_panic]| avvertendo il compilatore che ci
aspettiamo che la funzione vada in panic. Verifica che il codice fallisca
quando deve effettivamente fallire.

\begin{minted}[breaklines]{rust}
#[test]
#[should_panic]
fn test_divide_by_zero() {
  divide(10,0);
}
\end{minted}

I test devono verificare:

\begin{itemize}
  \item I casi normali
  \item I casi limite come divisione per 0, accesso al primo e all'ultimo elemento di un contenitore, etc.
  \item La corretta identificazione/gestione/propagazione degli errori
\end{itemize}

\begin{tcolorbox}
  \textbf{Note:} I test servono anche a testare errori!
\end{tcolorbox}

\section{Refactoring: miglioriamo il codice}

Nel momento in cui dobbiamo testare una funzione vi sono due possibilità

\begin{itemize}
  \item Le specifiche non sono chiare, non sappiamo come gestire un
        errore. Con il linguaggio naturale sarebbe difficile esprimere tutte le casistiche
  \item Quando mi rendo conto che il comportamento non può essere determinato
        dal cliente finale, dato che è una scelta progettuale.
        A questo punto si è costretti a riflettere come migliorare il codice (ritornare un Option o un Result al posto di un intero, etc.)
\end{itemize}

\begin{center}
  \begin{minipage}{0.45\linewidth}
    \begin{minted}[breaklines]{rust}
fn divide(a: i32, b: i32) -> Option<i32> {
  if b == 0 { None }
  else { Some(a / b) }
}
\end{minted}
  \end{minipage}%
  \hfill
  \begin{minipage}{0.45\linewidth}
    \begin{minted}[breaklines]{rust}
#[test]
fn test_divide_safe() {
  assert_eq!(divide(2,1), Some(2));
  assert_eq!(divide(1,0), None);
}
\end{minted}
  \end{minipage}
\end{center}



Questo processo ha reso il nostro codice più safe.

\begin{tcolorbox}
  \textbf{Note:} Niente panic e questo implica un'API più sicura
\end{tcolorbox}

\section{Test di integrazione}

Fino ad ora abbimao visto i singoli test, ma il nostro sistema è
composto da varie funzioni che ne chiamano altre e che interagiscono tra loro.

Un test di integrazione valuta il comportamento all'interfaccia di due moduli
software. Si focalizza sul determinare la correttezza di tale interfaccia,
evidenziando le incongruenze tra le parti che stanno interagendo

% Per questo dobbiamo complicare i test e iniziare a palrale di test di
% intrgazione o integration test.

% Guardiamo l'interazione tra due o più moduli software per verificare
% se funzionano correttamente insieme.

Come nel caso dei test di unità, è costituito da frammenti di codice che
sollecitano l'interazione tra due parti:

\begin{itemize}
  \item A differenza dei test di unità, tuttavia, ignora volutamente la
        struttura interna dei moduli che stanno interagendo, assumendo il loro
        corretto comportamento - sul piano individuale - alle specifiche definite.
        Infatti parliamo di test a black box.
  \item Per questo motivo viene eseguito solo su oggetti che hanno
        correttamente superato il test di unità
\end{itemize}

% Mentre nell'unit test posso scegliere con presicone i casi limiti in questo caso
% li devo trattare a black box. se copllettivamente rispetto all'imput danno
% l'output atteso.

% Poiché siamo a balckbox applichero l'integratopn test dopo aver testato
% i test di unità.

% Inoltre gli intregation test sono più difficili e costoso da gestire in caso di errore


I costi delle modifiche che occorre introdurre se un test di integrazione
fallisce sono generalmente più elevati. In quanto richiedono il ridisegno di
una o entrambe le parti che interagiscono.

Questa tipologia di test sono co-progettati da sviluppatori e tester, ma eseguiti
solo dagli ultimi.

      \item Gli errori del livello di persistenza siano

\section{Il flusso di lavoro con i test}

\begin{enumerate}
  \item Si scrive una funzione
  \item Si scrivono i test che ne verificano il comportamento
  \item Si esegue cargo test
  \item Si correggono gli errori che vengono riportati
  \item Si ripete fino a che il programma è completo

\section{Test in Rust}

I \textbf{test di unità} possono essere scritti nel modulo da testare o, meglio, in un
suo sotto-modulo chiamato convenzionalmente `tests'.

Il sotto-modulo contenente i test è preceduto dall'annotazione \mintinline{rust}|#[cfg(test)]|.
Questo informa il compilatore che il codice contenuto al suo interno deve essere
incluso solo quando la compilazione avviene con il comando \verb|cargo test|.\newline

I \textbf{test di integrazione} sono invece contenuti in una cartella separata denominata
tests, a lato della cartella src del progetto.

\begin{itemize}
  \item Sono scritti come se i singoli frammenti di codice fossero i
        consumatori del crate che deve essere testato
  \item I file sorgente all'interno della cartella di test importano i simboli
        pubblici oggetto di valutazione tramite istruzioni di tipo \mintinline{rust}|use...|
  \item Solo le librerie possono avere test di integrazione: per questo si
        creano programmi formati da un eseguibile contenente un main banale e da una
        libreria che contiene la logica applicativa
\end{itemize}

\subsection{Asserzioni}

Rust offre varie macro procedurali per verificare le asserzioni, tra cui

\begin{itemize}
  \item \mintinline{rust}|assert!( boolean_condition ) | - impone che la condizione sia vera
  \item \mintinline{rust}|assert_eq!( expected, actual ) | - impone l'eguaglianza tra i due valori
  \item \mintinline{rust}|assert_ne!( expected, actual ) | - impone la disuguaglianza tra i due valori
\end{itemize}

Per verificare che un'espressione generi la condizione di panico, è possibile
annotare il test anche con l'annotazione \mintinline{rust}|#[should_panic(expected = "msg")]|.
In questo caso, viene verificato che venga generata una condizione di panico riportante "msg".

Se una funzione di test restituisce un valore di tipo \mintinline{rust}|Result<T, Error>|, è
possibile utilizzare la condizione di errore che indica che il test è fallito.


\section{Eseguire i test}

Il comando \verb|cargo test| ricompila il programma con la direttiva "test" ed esegue
tutti i test contenuti nel package. Compresi quelli eventualmente presenti all'interno
della documentazione.
Viene riportato un report dettagliato che infica ogni singolo fallimento, dove
viene evidenziato il risultato atteso e quello realmente ottenuto seguito da un
riassunto con il nome di tutte le funzioni di test che sono fallite.

È possibile eseguire solo alcuni test, specificando il nome della funzione, o una sua
sottoparte, come ulteriore parametro del comando.

\begin{center}
  \mintinline{rust}|cargo test add_ |  esegue solo i test che contengono "add\_" nel nome
\end{center}

Se uno o più test è decorato con l'attributo \mintinline{rust}|#[ignore]|, viene
normalmente tralasciato dall'esecuzione, a meno che non vengano inclusi esplicitamente con
\begin{center}
  \mintinline{rust}|cargo test -- --ignored|  esegue solo i test ignorati
\end{center}


\section{Automatizzare la creazione di test}
Alcui sistemi devono essere provati con molti dati diversi, una lib può essere
rstest dando la possibilità di scrivere funzioni con parametri paramtrici
invocando la funzione test più volte tante quante sono i case definiti.


\subsection{Test parametrici con rstest}

Ogni singolo test è basato sul paradigma AAA, Arrange, Act, Assert. La fase di
Arrangement porta spesso a creare codice ripetitivo, volto a popolare strutture
dati con i necessari valori iniziali necessari all'esecuzione del test.
Normalmente, le funzioni di test sono prive di parametri, dovendo poter essere
invocate direttamente dal motore di test.

La libreria \textbf{rstest} permette di creare test parametrici, costituiti cioè
da funzioni dotate parametri in ingresso. Tali funzioni devono essere precedute
dall'attributo \mintinline{rust}|#[rstest]|

I parametri possono essere forniti in due modi alternativi:

\begin{itemize}
  \item Tramite funzioni annotate con l'attributo \mintinline{rust}|#[fixture]|,
        il cui nome deve coincidere con il nome del parametro di ingresso presente nei test
  \item Tramite un elenco di tuple alternative, descritte tramite l'attributo \mintinline{rust}|#[case(...)]|
\end{itemize}



\begin{minted}[breaklines]{rust}
use rstest::rstest;
#[rstest]
#[case(1, 2, 3)]
#[case(0, 0, 0)]
#[case(-1, 1, 0)]
fn test_sum(#[case] a: i32,
            #[case] b: i32,
            #[case] expected: i32) {
  assert_eq!(sum(a, b), expected);
}
\end{minted}


\section{Riassunto}

\begin{itemize}
  \item Verificano la correttezza dell'interazione tra due o più moduli
  \item Validano il contratto dell'interfaccia (tipi, semantica, protocollo di chiamata)
  \item Assumono che i singoli moduli abbiano già superato i test di unità
  \item Individuano:
        \begin{itemize}
          \item Incongruenze semantiche
          \item Errori di orchestrazione
          \item Problemi di gestione degli errori
          \item Violazioni di invarianti condivise
        \end{itemize}
  \item In Rust:
        \begin{itemize}
          \item Collocati nella cartella tests/
          \item Compilati come crate separati
          \item Testano esclusivamente l'API pubblica
        \end{itemize}
  \item Costi:
        \begin{itemize}
          \item Setup più complesso
          \item Correzioni architetturali potenzialmente costose
        \end{itemize}
\end{itemize}
